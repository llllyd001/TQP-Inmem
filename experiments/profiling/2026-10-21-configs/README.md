# 2026-10-21 Configuration Comparison: S3 + S2 / S4 Combinations and P1

## Objective
Under identical conditions, measure the GPU memory effects of slab-side combinations (S3+S2, S3+S4, S3+S2+S4) and PyTorch-side options (P1: expandable segments; control: `empty_cache` after every operator), as well as total device need for S3+P1 and the full combination; also verify that results match the reference run.

## Configuration
- RTX 5080, SF 5, 7, 10; pool size is the last successful size in E3; Q21 SF10 is skipped (baseline cannot run).
- For each (SF, query), run the reference once (no new flags), then run the following configurations sequentially, each with `--mem_profile --mem_trace`:

  | Configuration | Arguments |
  |---|---|
  | `s3_s2` | `--free_dead --slab_eps 0.01` |
  | `s3_s4` | `--free_dead --coalesce_every` |
  | `s3_s2_s4` | `--free_dead --slab_eps 0.01 --coalesce_every` |
  | `p1` | `PYTORCH_ALLOC_CONF=expandable_segments:True` |
  | `p1_empty` | `--empty_cache_per_op` |
  | `s3_p1` | `--free_dead` + expandable segments |
  | `s3_s2_s4_p1` | All |

- Shared GPU: before each run, wait until free GPU memory is at least the query's baseline reserved peak plus 0.5 GB. Memory metrics are per-process; `device_used_*` includes other users' usage and is not used.
- Compare results with the reference run using `test_main.py` rules (10 significant digits).
- Server logs: `~/runs/tqp/*-configs/`; result files: `~/runs/tqp/configs-data/results/` (`.out` files are excluded from the repository).

## Files
| File | Contents |
|---|---|
| `measure_configs.py` | Measurement script |
| `trace/<config>/` | Raw records (same as the S3 experiment: queries, ops, allocs, reads, frees, oom) |
| `runs.txt` | Status and result comparison for each run |

Derived data is generated by `report/make_data.py` in `report/plotdata/` (slab high-water mark, cached unused memory, total device need, correctness statistics).

## Main Results
- Total slab high-water mark (GB):

  | SF | baseline | S3 | S3+S2 | S3+S4 | S3+S2+S4 |
  |---|---|---|---|---|---|
  | 5 | 50.04 | 29.80 | 22.61 | 26.44 | 21.71 (−57%) |
  | 7 | 65.60 | 41.76 | 31.62 | 37.72 | 30.36 (−54%) |
  | 10 | 71.48 | 48.12 | 42.03 | 44.36 | 40.71 (−43%) |

  Consistent with offline replay (SF10 S3+S2: measured 42.03, replay 42.027; S3+S2+S4: 40.709 vs. 40.709).
- P1 (SF10, 21 queries): total memory cached by PyTorch but not in use decreases from 7.67 → 1.93 GB (expandable segments), compared with 5.70 GB for the `empty_cache` control. Q10: 3.23 → 0.41 GB; Q1 increases from 0.01 to 0.48 GB.
- Total device need summed over queries (SF10): baseline 129.9 → S3 106.5 → S3+P1 100.7 → full combination 93.3 GB (−28%).
- Correctness: 64 of 65 runs per configuration match the reference; mismatches are SF10 Q16 (all 7 configurations agree, with only the reference differing) and SF5 Q21 with `p1_empty`. See the next section for the cause.

## Result Mismatches
TQP's hash aggregation (`operators/aggregate.py:320-325`) generates random hash coefficients on each run and distinguishes groups solely by hash value; two groups with the same hash are merged, producing incorrect counts that may vary between runs. In the SF10 Q16 reference run, the Brand#59 group had a count of 72 (64 in all other 7 runs). This is behavior of the original system, unrelated to memory optimization; see `../2026-10-21-determinism/` for confirmation by repeated runs of the unmodified program.
