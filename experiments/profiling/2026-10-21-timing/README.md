# 2026-10-21 Runtime: Optimized Configurations Relative to Baseline

## Objective
Measure the effects of S3, S2, S4, P1, and their combinations on query runtime (Trade-offs in the report).

## Configuration
- RTX 5080, SF10, 21 queries (Q21 cannot run at SF10). Pool size is the last successful size in E3.
- Configurations: `baseline`, `s3` (`--free_dead`), `s3_s2_s4` (`--free_dead --slab_eps 0.01 --coalesce_every`), `p1` (`PYTORCH_ALLOC_CONF=expandable_segments:True`), `s3_p1`, `s3_s2_s4_p1`. No measurement tools are enabled.
- One fresh process per (configuration, query), running the query 4 times consecutively (`--q Q Q Q Q`); discard the 1st run as warmup and record the remaining 3. Timing uses `main.py`'s `time_elapsed` (disk reads and output time already excluded).
- Before each process starts, require total device memory usage $\le 0.5\,\mathrm{GB}$ (`mem_sweep.wait_for_quiet_gpu`) to avoid contention with other users' jobs
- `s3_s2_s4` and `s3_s2_s4_p1` used the uncorrected $N$ for approximately the first 6 queries (slightly larger blocks). Block size affects slab internal fragmentation (memory data comes from `2026-10-21-configs` after the $N$ correction and is unaffected) and slab bookkeeping overhead (microseconds, compared with query times of 7–248 ms), but does not change query results or GPU computation, so the timing conclusions are unaffected.
- Server logs: `~/runs/tqp/20261021-011803-timing/`.
