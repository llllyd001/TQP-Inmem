# 实验记录规范

每次正式实验，把结果交给用户之前，都要先完成下面三件事。这是用户 2026-10-12 定下的要求。

1. **保留所有原始数据列。** 原始 CSV 按服务器输出原样保存，不删列、不改单位、不四舍五入。
2. **添加派生列，反映这次实验的间接性质。** 例如利用率、碎片、平均每次的大小、比值、总需求。派生列放在 `<名字>_derived.csv` 里，插在计算它所用的原始列旁边；原始列一列不少。
3. **把数据可视化。** 每次实验至少给出能看清主要结构的图：条形图、堆叠图、折线图、散点图等，按数据的作用来选。压测 OOM 边界的实验，必须有"规模 → 峰值"的折线图，并把显卡容量画成参考线。

## 目录结构

代码和实验数据都在仓库的 `experiments/profiling/`（2026-10-13 起）：

```
TQP-Inmem/experiments/profiling/
  README.md                  本规范
  mem_profiler.py            查询级测量工具（main.py --mem_profile <csv>）
  mem_sweep.py               批量运行：每个"查询 × SF"一个独立进程，自动选择池大小
  svgplot.py                 画图工具（只用 Python 标准库；用无头 Chrome 把 SVG 转成 PNG）
  YYYY-MM-DD-<标签>/         一次实验：脚本、数据、图表和记录
    measure_<实验>.py        这次实验专用的测量代码（如果有；早期实验以 python -c 方式运行）
    analyze_<实验>.py        原始 CSV → 派生 CSV + 图表；读写自己所在的文件夹
    <名字>.csv               原始数据（单位：字节、秒）
    <名字>_derived.csv       原始列 + 派生列
    stdout.log               服务器的原始输出（*.log 被 git 忽略，只留在本地）
    figures/*.svg, *.png     图表
    README.md                实验记录（结构见下），写明用了哪个脚本
```

**脚本的修改规则：** 共用工具（mem_profiler、mem_sweep、svgplot）放在 `experiments/profiling/` 顶层；每次实验专用的脚本放在它自己的实验文件夹里。已经被某次实验用过的 `measure_*.py`，以后不要改它的测量逻辑。要改就另建一个新文件，这样旧实验永远能找到当时的代码。`analyze_*.py` 可以改，改完重新运行一遍即可。

**在服务器上怎么运行：** 先 `sync_server.sh`，再 `run_server.sh --gpu -- python experiments/profiling/mem_sweep.py ...`。早期的 `measure_*.py` 需要以 `python -c "$(cat ...)"` 方式运行，脚本里不能有 `$` 和反引号。

服务器上对应的原始日志在 `~/runs/tqp/<时间>-<标签>/`，由 `run_server.sh --log` 生成。

## 实验 README 的结构

1. 目的
2. 环境与代码：GPU、驱动、CUDA、PyTorch 版本，提交哈希，是否有未提交的改动，数据规模，池设置，服务器日志路径
3. 方法：测了什么、怎么测
4. 文件，以及**派生列定义表**（派生列名、放在哪一列后面、公式、含义）
5. 结果表
6. 图表：每张图写两句，"怎么读"和"看到什么"
7. 派生指标
8. 观察（已测到的）
9. 推测（还没验证）
10. 和预期或文档的对照
11. 延伸：结论或推测 → 新问题 → 对应实验 → 在 schedule 里的位置
12. 局限

从数据得出结论的方法，见 Articles 基础知识 08 模块 §7 "五步法"。

## 画图约定

- **图上的所有文字都用英文**（标题、副标题、坐标轴、图例、标签）。README 里的说明仍然用中文。
- 颜色按固定顺序使用 `svgplot.SERIES`，不循环。同一个量在不同图里用同一种颜色。
- 不用双 y 轴。两个量级不同的指标，分成两张图。
- 只给关键的点加数值标签（最大值、离群点），不要每个点都标。
- 标题直接写结论或含义；副标题写"怎么算的"。
- 每张图出完都要打开 PNG 看一眼，检查文字有没有重叠、是否超出边界。
