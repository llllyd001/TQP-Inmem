\title{\Large\bfseries Where Does the GPU Memory Go?\\ Operator-Agnostic Memory Management for TQP-Inmem}
\author{Mingqing Lin\\ University of Michigan}
\date{}

\begin{document}

\begin{abstract}
Tensor Query Processing (TQP) runs SQL on tensor runtimes and is fast on GPUs, but
TQP-Inmem keeps all data in device memory and runs out of memory on a 16\,GB GPU
at TPC-H scale factor (SF)~10. I decompose where the memory goes during a query:
a fixed-block slab pool that never frees during a query, and PyTorch's caching
allocator outside it. With an operator-level trace and exact offline replay, I
find that data no longer needed by any later operator is the largest part of the
slab peak. I implement four memory-management changes that are independent of
any query or operator: last-use reclamation driven by the query plan, coalescing
on every free, a block size planned before execution from a waste budget, and
PyTorch's expandable segments. Together they lower the slab peak by 43--57\%,
PyTorch's reserved-but-unused memory by 75\% and the device need at SF~10 by 28\%, so
all 22 queries run at SF~11 where one failed at SF~10, at a 2.9\% run-time cost and with
results matching the unmodified system.
\end{abstract}

% ---------------------------------------------------------------
\section{Motivation}
\label{sec:motivation}
TQP~\cite{he2022tqp,cui2026tqppp} compiles relational queries into tensor programs
and executes them on tensor runtimes such as PyTorch, which makes GPU query processing
fast without writing custom kernels. TQP-Inmem, the in-memory variant studied here,
keeps every column and intermediate result in GPU memory. Its speed therefore comes with
a hard limit: the data size it can handle is bounded by device memory.
On an RTX~5080 (16\,GB), Q21 fails at SF~10 and Q9 needs 16.2 of the 16.6\,GB the device
offers (\cref{fig:ranking}).

This report optimizes how TQP-Inmem \emph{plans and manages} GPU memory, from the
system side, so that it can process queries on larger data. I keep the setting fixed:
a single GPU, all data resident in device memory, results that match the unmodified
system, and any slowdown reported. All methods are operator-agnostic and query-agnostic:
they depend only on the query plan and the allocator, not on tuning against TPC-H.

\section{Background: Memory of One Query}
\label{sec:background}
GPU memory during a TQP-Inmem query has four parts (\cref{fig:layout}).
\begin{itemize}
\item \textbf{CUDA context} ($\approx$0.3\,GB), fixed per process.
\item \textbf{Slab pool.} One \code{torch.empty} byte tensor (4\,GB by default) is
  allocated once and carved into fixed 40\,MB blocks with first-fit placement. Scanned
  columns and every operator output are copied into it. Blocks are only borrowed during
  a query and all are returned at the end (\code{free\_all}).
\item \textbf{PyTorch caching allocator.} Temporaries inside operators (hash tables,
  join candidates, the scan's staging copy) are ordinary PyTorch tensors. Freed tensors
  return to PyTorch's cache (\emph{reserved}), not to the GPU~\cite{pytorchmem}.
\item \textbf{Free device memory.}
\end{itemize}
The split between the slab and PyTorch is \emph{static}: the slab size is chosen at
start-up and neither side can use the other's free space. A query fails in two ways:
the slab has no contiguous run of free blocks (a Python \code{MemoryError}), or PyTorch
cannot obtain device memory (\code{torch.OutOfMemoryError}).

\section{Diagnosis: Why Memory Runs Out}
\label{sec:diagnosis}
I group the possible causes into three ordered categories (\cref{tab:causes}).
The order matters: layout problems depend on which allocations exist and when they
are released, so data and lifetimes must be settled before layout is evaluated.

\begin{table}[t]
\centering\small
\setlength{\tabcolsep}{3pt}
\begin{tabular}{@{}llp{5.1cm}@{}}
\toprule
Category & ID & Cause \\
\midrule
\multirow{2}{*}{Data itself} & S1 & Data that must be resident at the same time (live peak) exceeds the slab \\
 & P2 & Operators create large temporaries outside the slab \\
\midrule
Lifetime & S3 & The slab keeps columns no later operator reads (dead data) \\
\midrule
\multirow{4}{*}{Layout} & S2 & Internal fragmentation: the last block of each allocation is partly empty \\
 & S4 & External fragmentation: free slab blocks are not contiguous \\
 & P1 & PyTorch reserved memory is split across segments \\
 & -- & Static split between slab and PyTorch \\
\bottomrule
\end{tabular}
\caption{Possible causes of out-of-memory failures.}
\label{tab:causes}
\end{table}

\textbf{Data itself.} S1 bounds every storage scheme from below: no layout can go below
the live peak. P2 is the size of operator temporaries, e.g.\ a join that expands
candidate pairs into a dense matrix. Both are reduced only by changing what data is
produced (representation, late materialization~\cite{abadi2007materialization}, or
operator algorithms).

\textbf{Lifetime.} Because the slab never frees during a query, its peak equals the sum
of all scanned columns and all operator outputs. The live data at any moment is
usually much smaller. A reference-counting allocator does not help by itself: every
column stays reachable from the executor's column map (\code{tensor\_group}) until the
plan ends, so it is never \emph{unreachable}, only \emph{unused}. Recognizing it as dead
requires looking ahead in the plan.

\textbf{Layout.} With data and lifetimes fixed, the same bytes can still occupy more
space. In the slab, each allocation is rounded up to whole 40\,MB blocks (S2), and once
blocks are freed mid-query, free runs can be separated by live blocks (S4). In PyTorch,
each \code{cudaMalloc} returns a separate segment and free space in different segments
cannot be combined (P1). Finally, the static split forces each side to reserve for its
own peak even when the two peaks occur at different times.

\section{Methodology}
\label{sec:method}
I take the system route: change how memory is planned and managed, without changing
the plan, the operators, or the data representation. This covers S3, S2, S4, P1 and the
static split; S1 and P2 require changing what is computed. For each cause I give
candidate methods and their trade-offs; \cref{sec:impl} describes the ones I built.

\subsection{Slab}
\textbf{S3: last-use reclamation.} Freeing needs two answers: \emph{will anyone read
this column later?} and \emph{does anyone still hold this memory now?} Neither alone
saves slab memory. Removing a name from \code{tensor\_group} is always safe (a too-early
removal raises \code{KeyError} at the next lookup) but returns no slab block; reference
counting never fires because the map still holds every column.
\begin{itemize}
\item \emph{Allocator integration.} Make the slab a PyTorch custom allocator so that each
  allocation is its own storage and PyTorch's reference count returns the block. Safety
  holds by construction and temporaries could share the slab, but PyTorch's many small
  tensors would each take a block, the cache would delay returns, and it needs a compiled
  extension. I do not adopt it: the slab's fixed blocks likely also serve TQP's out-of-core
  execution (outside the scope of this report), so I keep the slab itself unchanged.
\item \emph{Executor-level reclamation.} Keep the slab unchanged. After each operator,
  drop the names whose last reader has run, then free every slab allocation that no
  remaining column points to, checked by real device address. Safety rests on one
  checkable invariant: between operators, GPU data is reachable only through
  \code{tensor\_group}, because operators are functions whose locals die on return.
  A freed allocation goes back to the slab's own free list for reuse later in the query;
  the device memory stays with the slab, so the gain is a lower high-water mark and thus
  a smaller slab.
\end{itemize}
The last reader of a column comes from the plan: Spark lists the input columns of every
non-scan operator, and the output operator lists its outputs. This single rule covers all
operator types.

\textbf{S4: coalescing and placement.} Two knobs control holes: \emph{when} adjacent free
runs are merged (the original pool merges after every sixth free) and \emph{where} a new
allocation goes (first-fit, best-fit, or lifetime-aware placement that puts short-lived
data at the high end). Merging only edits a list of a few dozen (start, length) pairs and
moves no data. Lifetime-aware placement needs a threshold for ``short-lived''.

\textbf{S2: block size from a waste budget.} Each allocation wastes less than one block,
so at the peak the internal fragmentation is at most $N\cdot b$, where $N$ is the number of
simultaneously live slab allocations and $b$ the block size. $N$ is a property of the plan
(it is identical at SF~5 and SF~10). Given the slab capacity $P$ and a tolerated waste
fraction $\varepsilon$, I choose the largest $b$ with $N\cdot b \le \varepsilon P$ before
the query runs. The only parameter, $\varepsilon$, has a direct meaning. A fixed tiny
granularity removes the parameter but decouples the block from any transfer unit.

\subsection{PyTorch Reserved Memory}
\textbf{P1: PyTorch segments.} PyTorch's allocator already merges a freed block with its free
neighbours immediately and places requests best-fit, so the S4 knobs bring nothing there.
What remains is fragmentation across \emph{segments}: each segment is a separate driver
allocation, free space in two segments cannot be merged, and a segment holding even one
live tensor cannot be returned.
\emph{Expandable segments}~\cite{pytorchmem} reserve one large virtual range and map
physical pages on demand; fully free pages can be unmapped and remapped elsewhere, so
holes cost virtual addresses rather than device memory, the same idea as paging in
PagedAttention~\cite{kwon2023paged}. Mapping changes page tables only and moves no data,
but growing a segment may take several driver calls. Calling \code{empty\_cache} after
every operator returns fully free segments instead, at the cost of re-allocating them.

\textbf{Static split.} The total need under a static split is the slab peak plus the
PyTorch peak, while a shared space needs only the maximum over time of their sum.
Two ways close the gap: let PyTorch temporaries allocate from the slab (the allocator
integration above), or size the slab to the post-reclamation need so that its savings
go to PyTorch. I adopt neither: the first changes the slab itself (see S3), and the second
needs the slab's need before the query runs, which depends on the data and not only on the
plan.

\section{Implementation}
\label{sec:impl}
All changes are command-line switches that are off by default; with every switch off
the program behaves exactly as before. The changes add 78 lines
(\code{utility/lifetime.py}) and about 60 lines in \code{main.py} and the slab pool.

\textbf{Measurement.} \code{-{}-mem\_trace} records, per operator, every slab allocation
(start block, blocks, requested bytes), the slab blocks each operator reads, and PyTorch's
allocated, reserved and split-free bytes. Reads are captured by replacing
\code{tensor\_group} with a dictionary subclass that logs each lookup and maps the tensor's
\emph{device address} (\code{data\_ptr} and its size and strides) to slab blocks, so
renamed columns, slices and outputs without a block tag are all attributed correctly.
Records stay in host lists and are written when the query ends, so tracing allocates no
GPU memory; with and without tracing, all query-level memory counters are identical.
Slab policies are evaluated by replaying the trace in a pure-Python copy of the pool:
placement changes neither which allocations happen nor which data is read, so the replay
is exact; it reproduces all 65 measured high-water marks of the S3 runs.

\textbf{Correctness.} With all switches on, plus \code{-{}-poison\_freed} and
\code{-{}-check\_refs}, all 22 queries match the SF~1 reference shipped with the repository
under its test rule (10 significant digits); bit-exact comparison is not meaningful because
GPU floating-point sums are not ordered.

\subsection{Slab}
\textbf{S3.} Before a plan runs, \code{last\_uses} maps every column to the last operator
whose Spark \code{Input} list (or, for the output operator, \code{Output} list) contains it.
After operator $j$ (\cref{fig:reclaim}), \code{free\_dead} deletes every column whose last
use is $\le j$, collects the slab blocks still covered by the remaining columns' device
address ranges, and returns every allocation none of whose blocks is covered to the slab's free list. Mask
columns that TQP adds for late materialization are not in Spark's lists and are kept.
Two test switches check the safety argument: \code{-{}-poison\_freed} fills returned blocks
with \code{0xFF}, so any read after free corrupts the result, and \code{-{}-check\_refs}
scans all live CUDA tensors with Python's garbage collector after each release and fails
if one points into a returned block.

\textbf{S4.} \code{-{}-coalesce\_every} makes the pool merge adjacent free runs on every
free instead of every sixth. Placement stays first-fit, which needs no threshold.

\textbf{S2.} With \code{-{}-slab\_eps}~$\varepsilon$, after loading a query's plans and
before it runs, \code{max\_live\_columns} computes $N$ from the plan as the maximum over
operators of the columns still live when the operator starts plus the columns it outputs:
every output gets a fresh allocation while the inputs are still held. A column is born at the
first operator that outputs it and dies after its last use (at the plan's end without S3, and
always for masks). The pool, still empty at that point, is reset to blocks of
$\lfloor \varepsilon P / N \rfloor$\,MB (at least 1\,MB).

\subsection{PyTorch Reserved Memory}
\textbf{P1.} Expandable segments are enabled with the environment variable
\code{PYTORCH\_ALLOC\_CONF=expandable\_segments:True}; no code changes.
\code{-{}-empty\_cache\_per\_op}, a control for P1, calls \code{torch.cuda.empty\_cache()} after each operator.

\section{Experiments}
\label{sec:exp}
\subsection{Setup and Measurement}
\textbf{Setup.} One RTX~5080 (16.6\,GB usable as reported by PyTorch), PyTorch~2.14 with
CUDA~13.0, TPC-H data at SF~5, 7 and 10, all 22 queries. Each query runs in a fresh
process. I report the \emph{device need} of a run: the slab high-water mark (including
holes), plus PyTorch's reserved memory outside the slab, plus the CUDA context (0.30\,GB).
Memory is measured without warm-up (a warm-up changes no memory counter); time is measured
after one warm-up run with tracing off. The GPU was shared with another user's jobs:
each run starts only when free memory covers the query's measured need, and timing and
OOM-boundary runs start only when the GPU is otherwise idle.

\textbf{Slab size.} The slab is allocated once per process with a size $P$ set on the
command line. With a fixed block size, what happens inside the slab does not depend on
$P$: allocations and frees follow the plan, first-fit always searches from block~0, and a
run that fits never touches a block beyond its high-water mark (exact replay reproduces
every measured mark). Any $P$ at or above the high-water mark gives the same run. Two
consequences follow. (i) For the memory measurements, each (query, SF) uses the slab size at
which the unmodified system ran in the search below, the same $P$ for every configuration,
and I report the high-water mark rather than $P$; the device need is thus the memory a slab
sized to its high-water mark would take, computed rather than run. (ii) Under any fixed $P$,
a query fits the slab iff its high-water mark is at most $P$, and fits the device iff $P$
plus its PyTorch memory and the context do; lowering either part can only let more queries
run at the same $P$. S2 is the one switch whose block size depends on $P$ ($b=\varepsilon P/N$),
but its bound $I\le\varepsilon P$ holds for every $P$. PyTorch's memory is measured with free
memory to spare; when memory is short, PyTorch first releases its cache and retries.

\textbf{Slab-size search.} Whether a query can run at an SF at all is decided by real runs.
The search starts from TQP's default 4\,GB slab (or the previous SF's high-water mark scaled
by the SF ratio, plus 10\%). A slab overflow grows $P$ by 1.5$\times$; a device OOM shrinks it
to the slab memory held at the failure plus 10\%, since an oversized slab takes room from
PyTorch; once both kinds of failure are seen, it bisects between them. A query is OOM at an
SF when the interval closes to 0.2\,GB without a successful run (cap 14\,GB). Each query
gets its own $P$, and both systems use the same search.

\textbf{OOM at SF 10.} \Cref{fig:ranking} ranks the queries by device need. Q21 does not
run at any slab size, and Q9 needs 16.15\,GB of the 16.6\,GB device.

\subsection{Effect of Each Method}
\textbf{Correctness.} Each optimized run is compared with a reference run of the
unmodified system on the same data. Of 520 comparisons at SF~5--10, two differ, and
both trace back to the unmodified system: its hash aggregation draws random hash
coefficients per run and separates groups only by hash value
(\code{operators/aggregate.py}), so two groups occasionally merge and a count grows
(e.g.\ 64 to 72 in Q16). In the Q16 case the \emph{reference} run was the outlier: five fresh
unmodified runs and all seven optimized configurations agree with each other; in the other
case five repeats of the same configuration match the reference.

\textbf{Slab: S3, S2 and S4.} \Cref{tab:slab} compares the slab
high-water mark (including holes). Reclamation (S3) removes 33--40\% of the slab peak;
replaying the trace with the recorded frees reproduces every measured high-water mark. On top of S3, the waste-budget block

\section{Results}
\label{sec:results}
\begin{itemize}
\item \textbf{Slab.} Last-use reclamation, a block size planned from a 1\% waste budget, and
  coalescing on every free lower the summed slab peak by 43--57\% at SF~5--10. Reclamation
  alone gives 33--40\%.
\item \textbf{PyTorch.} Expandable segments reduce reserved-but-unused PyTorch memory by
  75\% at SF~10 (7.7 to 1.9\,GB summed).
\item \textbf{Device need.} Together, the device need summed over queries at SF~10 falls by
  28\%; Q9 needs 13.3 instead of 16.2\,GB, and Q10 6.8 instead of 12.1\,GB.
\item \textbf{Scale.} All 22 queries now run at SF~11 on the 16\,GB GPU, where Q9 and Q21
  previously failed; Q9 runs up to SF~12 instead of 10, and Q21 up to SF~11 instead of 9.
\item \textbf{Cost.} Results match the unmodified system up to its own run-to-run variation,
  and queries are 2.9\% slower on geometric mean (\cref{sec:tradeoffs}).
\end{itemize}

\section{Trade-offs}
\label{sec:tradeoffs}
\textbf{Run time.} \Cref{tab:time} compares query time at SF~10 (median of three runs after

\textbf{Waste budget versus block count.} A smaller $\varepsilon$ gives smaller blocks and a
tighter bound on padding (\cref{fig:eps}); it does not increase the number of allocations or
free-list entries, which depend only on the plan. The cost of a small block appears only
if a later component needs large fixed units, e.g.\ for transfers between host and device.

\textbf{Complexity and scope.} All four changes are plan- and allocator-level: about 140
lines of Python, no compiled code, no change to any operator, and each is a switch. S3
relies on one invariant (between operators, device data is reachable only through the
column map), which \code{--check\_refs} verifies generically rather than per query. The
remaining limit is outside the slab: for the queries closest to the device limit, operator
temporaries dominate (\cref{fig:breakdown}), which memory management alone cannot remove.

\section{Other Thoughts}
\label{sec:other}
S1 and P2 change what data is produced rather than how it is stored, so they lie outside the
system route taken here. I have not implemented them, but each direction below should lower
memory further, at the price of changing the data representation or the operators. Like the
four changes above, they apply to an operator or a column type, not to particular queries.

\textbf{S1: less live data.} \emph{Narrower representation}: smaller integer types where the
value range allows, dictionary-encoded strings, and lightweight GPU compression
\cite{shanbhag2022tile} shrink every column and with it the live peak, at a decoding cost.
\emph{Late materialization}~\cite{abadi2007materialization}: after a filter or join, pass row
indices and fetch a column only where it is read, so fewer copied columns are live at once.

\textbf{P2: smaller temporaries.} Since operator temporaries dominate for the queries closest
to the limit (\cref{fig:breakdown}), this is the next lever. \emph{Scan into the slab}: copy a
host column directly into its slab allocation instead of first through a whole-column device
temporary. \emph{Join without a dense candidate matrix}: build candidate pairs from the actual
bucket lengths, leaving no padding~\cite{fegade2022cora}. \emph{No second copy on output}: write
an operator's result straight into the slab. \emph{Chunked operators}: probe or hash in pieces,
so a temporary is one chunk in size, as tiling does in FlashAttention~\cite{dao2022flashattention};
this costs more kernel launches. \emph{Operator fusion} through tensor compilers
\cite{ansel2024pytorch2,cui2026tqppp}: intermediates of fused operators never reach device memory.

\section{Reproduction}
\label{sec:repro}
\textbf{Environment.} NVIDIA GeForce RTX~5080 (16\,GB), driver 590.48.01, Python 3.12.14,
PyTorch 2.14.0+cu130 (CUDA 13.0). Set-up follows \code{Setup.md}; TPC-H tensors are generated
with \code{tpch-dbgen-tensors} (\code{./dbgen -s <SF>}); each measurement script with
\code{-{}-manage\_data} generates one SF, runs, and deletes it.

\textbf{Switches} (all off by default): \code{-{}-free\_dead} (S3), \code{-{}-coalesce\_every}
(S4), \code{-{}-slab\_eps 0.01} (S2), \code{PYTORCH\_ALLOC\_CONF=expandable\_segments:True}
(P1), \code{-{}-empty\_cache\_per\_op}; \code{-{}-mem\_profile <csv>} and \code{-{}-mem\_trace <dir>}
record memory; \code{-{}-poison\_freed} and \code{-{}-check\_refs} are safety tests. Example:
\code{python main.py -{}-SF 10 -{}-q 9 -{}-gpu\_pool\_gb 6 -{}-free\_dead -{}-slab\_eps 0.01 -{}-coalesce\_every}.

\code{report/README.md} lists the exact command for every table and figure. Older PyTorch
reads \code{PYTORCH\_CUDA\_ALLOC\_CONF} instead.

\textbf{Experiments.} Each folder in \code{experiments/profiling/} holds the measurement
and analysis scripts, raw CSVs (\code{trace/}), derived CSVs, figures and a README for one
experiment; \code{report/make\_data.py} builds the plotted tables in \code{report/plotdata/}
and \code{latexmk -pdf main.tex} builds this report.
